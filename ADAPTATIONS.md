# Controlled Spotify MCP integration

The fork retains upstream's API tools and transports. Changes are maintained on codex/controlled-playback, initially based on upstream e6c817482d25a41b068c2b231e3bc39c8c5d6e4a. The wstrinz and Dienert forks were reviewed as architectural references; their source was not copied into this increment.

## Session authentication

Set SPOTIFY_SESSION_AUTH=pkce and SPOTIFY_CLIENT_ID to a public Developer app ID. The app redirect must be http://127.0.0.1:8765/callback. Three additional tools begin authorization, read its status and close the session. The owner opens the returned link manually. Sign-in requests upstream's full scope set; no client secret is needed. Tokens remain in memory, refresh there and are discarded with cached SDK clients when the session closes. Process termination also discards memory. Legacy file-backed authentication remains available when this mode is unset.

The callback page is a separate presentation component adapted from the investigation controller. Its success page acknowledges receipt before token exchange, attempts tab closure after three seconds and provides a manual fallback. Confirm authorization with the status tool. Invalid callbacks do not exchange codes. Callback errors and URLs are not logged.

## Playback

playMusic and resumePlayback require an explicit discovered device and refuse fallback when it is unavailable. Set SPOTIFY_REQUIRE_DEVICE=true to require explicit devices for the remaining playback controls. Library and playlist commands are unaffected by this device rule. Granted OAuth scopes do not constitute instructions to modify account data.

playMusic supports context playback with numeric offset or offsetUri, plus positionMs. Results distinguish accepted requests from observed matching device/track state. A single state read does not verify advancing progress or prove sustained playback; subsequent getNowPlaying calls are required. A delayed provider update may initially report playbackObserved=false. Single-track URI playback remains available but is not established to work on every desktop build.

searchSpotify returns a track ID/URI that can be passed to playMusic on an explicitly selected device; skipToPrevious is also exposed. The seekToPosition tool adds absolute within-item seeking on an explicit active device. It reads the current item first, refuses a different active device or a position at/past a known duration, sends Spotify's seek command, then reports acceptance separately from a one-time observed device/item/position check. A delayed provider update can make positionObserved false after an accepted command. The check is a matching state observation, not proof of uninterrupted playback or causation. Seek uses the existing user-modify-playback-state scope; no new OAuth scope is required.

Generic JSON parse errors no longer become successful operations. Successful responses from the specific player control endpoints are treated as acknowledgements with no response document, even if opaque text is labelled JSON. The SDK fetch adapter normalizes these acknowledgements to an empty response; the direct helper follows the same endpoint/method rule. Failed HTTP responses, player reads and JSON-producing playlist mutations retain their normal validation/parsing. Upstream POSIX permission tests are skipped on Windows because they cannot validate Windows ACLs. Session mode does not write credential files.

## Verification

Build and run the Node test suite using a runtime satisfying package.json. New tests cover device fallback refusal, wrong-track observations, strict untargeted control rejection, PKCE, callback-state validation, valid token exchange and session closure. Live Spotify consent/playback and native chat connectivity are separate checks.

Acknowledgement regression tests exercise actual SDK pause/queue/skip calls against mocked successful opaque responses, the direct playback helper, rejected commands, malformed player reads and retained playlist JSON results. The correction requires a server reload to affect an already running MCP process; offline passing tests do not establish live behavior after reload.

The seek increment builds with the project-local Node 26 runtime. The full test suite reports 125 passes, zero failures and two Windows-inapplicable POSIX-mode skips. New tests cover a targeted seek, a delayed/nonmatching playback-state read, refusal of a different active device or a position at/past known duration, schema rejection of nonpositive positions, and stdio discovery of the added tool. Targeted Biome lint of changed source/test files passes; the repository-wide formatter check still fails on existing CRLF files.

After a Codex restart, the native MCP exposed seekToPosition and fresh memory-only consent succeeded. On an explicitly selected desktop device, album-context playback was eventually observed after an initial accepted-but-unobserved response. A targeted seek to 60 seconds returned accepted with positionObserved=false on the immediate read, then a follow-up state read showed the same track near 67 seconds. Next and Previous changed tracks in the expected order; a final pause was observed. An intervening resume returned a provider 403 restriction and was not treated as successful. The provider's playback reads can lag commands, so the immediate observation is deliberately not a guarantee of final playback state. No library or playlist mutation was made.

A second direct track-ID play request, made after the desktop device had been active, was accepted but still did not load or play the requested item on follow-up reads. Starting that same track through its known album context at its zero-based offset did play it, and the desktop was paused afterward. For this client, search-to-play should resolve the track's album and position with search/getAlbumTracks, issue an album-context play, then verify the observed track. A direct track URI remains available but is not a reliable fallback based on these trials.

## Playback observability and settings increment: 2026-10-23

Seven additional tools are implemented in playback-extras.ts. getPlaybackState returns selected structured fields from Spotify's player state, including millisecond progress, context, device identity, repeat/shuffle and available actions. waitForPlaybackState polls for a matching device and optional item, play state and progress range with a ten-second maximum. It reports a matched observation, not proof that the preceding command caused it. A timeout returns the last observed state without claiming success.

transferPlayback selects one currently available, unrestricted device and defaults to preserving play/pause state. setRepeatMode and setShuffle require that the explicitly selected device is active. All three separate API acceptance from one immediate observed state read. getTrack resolves a single catalog track, including its album and ISRC when provided. getRecentlyPlayedPage supports Spotify's after/before millisecond cursors and returns timestamps and playback context. No additional OAuth scopes or account-library mutations are involved. These capabilities have offline fixture coverage; live behavior remains unverified until a server reload and controlled trial.

The updated build and full Windows test suite pass: 131 passed, zero failed, and two POSIX permission tests skipped because they cannot verify Windows ACLs. Targeted formatter/lint and TypeScript checks pass for the new source and tests. The compact nested-field projection was corrected after the first live run.

After a Codex restart and fresh memory-only consent, all seven new tools were discovered. Live reads returned structured state, a known track's catalog metadata and a recent-history page. With no active playback device, transferPlayback activated the desktop with play=false and preserved the paused track. Repeat changed from context to off and back; shuffle changed from false to true and back. In each setting trial, the command was accepted while the immediate state read was stale, and a later read confirmed the requested value. waitForPlaybackState matched the paused desktop item. The session ended with the same paused item, repeat=context and shuffle=false. No library/playlist mutation, debugger attachment or capture occurred.

After the next MCP reload, a new session-only consent reached `phase=ready`, and `getTrack` returned compact album and artist fields without the upstream nested image/link payload. In a separate controlled playback check, `transferPlayback({ play: false })` selected the desktop while paused. Two album-context requests at different offsets were accepted; `waitForPlaybackState` and later `getPlaybackState` reads confirmed each requested track playing on that desktop device. Immediate `playMusic` observations were stale, so they are not used as confirmation. The last track was paused and a matching paused-state read was obtained. These checks validate the controller's observed device, item and play-state workflow under the tested client conditions; they do not validate Spotify's internal audio metadata or the debugger's event path.
